# LJ 章节稿：部署、备份恢复与综合权衡（v2）

状态：第5棒章节稿。日期：2026-11-07。课程依据为《作业要求.pdf》第2页（高可用、扩展性、灾备与成本）、第5页（设计权衡）和第6页（评估指标）[1]。统一模式和 ZC 查询负载以数据库为准；本节的性能数据仅为 Windows 本地合成实验。

## 3.3 部署、备份与恢复

### 部署边界

课程原型采用单机 SQLite WAL：统一模式、发布目录、审计和查询追溯表在同一数据库中，规划服务通过只读事务固定一个 `release_id`。数据库是可重建快照的唯一事实源；JSON 只作为导出或恢复演练的输入输出，不作为第二个可变事实源。生产目标是 PostgreSQL/PostGIS 主库加只读副本，规划服务保留短期内存图缓存，缓存以 `release_id`、风险数据集和规划配置为键。边缘节点只缓存已发布只读快照，发布和权限变更回主库完成。

复制与故障切换按数据角色区分：数据库文件、WAL、审计事件和发布哈希必须一起保护；内存中的 `route_graph_cache` 不备份，恢复后按发布重新构建。切换前先阻止发布和敏感导出，读取最后一个完整快照；切换后执行完整性、外键、发布链和历史查询核验，全部通过才恢复推荐。

### 备份流程和目标

1. 将系统置于可观察状态，记录 `operation_id`、当前指针和 WAL 大小。
2. 对 SQLite 使用在线 `Connection.backup()`；生产文件在备份前执行 WAL checkpoint，或把数据库文件与 WAL 作为同一备份集合。备份摘要、源库大小、开始/结束时间和发布指针写入备份记录。
3. 备份完成后保留源库，禁止用恢复文件覆盖唯一副本；备份副本进入加密对象存储并按保留策略归档。
4. 恢复到隔离路径后依次执行 `PRAGMA integrity_check`、`PRAGMA foreign_key_check`、发布父链与 `content_hash` 检查，再重放一条历史查询并比较保存的结果摘要。
5. 正常核验通过后才切换读流量；任何摘要不匹配、损坏、缺少父版本或外键错误都进入 `blocked`，不得显示为可用。

本轮实验使用两个合成发布（R0、R1，R1 的 `base_release_id=R0`）。在线备份后的正常恢复同时通过完整性、外键、发布链和历史 Q2 限制查询摘要比较；截断备份被完整性检查或数据库打开错误发现。实测结果见 [recovery.json](experiments/results/recovery.json)。这证明核验规则在该样例上能发现损坏，不证明生产 RTO。

RPO/RTO 是设计目标而非本机实测承诺：单机原型建议 RPO ≤ 15 分钟、RTO ≤ 30 分钟；空域发布期间优先保留最后一个已验收发布，宁可暂时停止新发布和受影响 Q1，也不返回版本混合结果。RPO 取决于 WAL/备份频率，RTO 取决于文件恢复、核验和重建派生图的规模，部署前必须用目标规模演练。

## 8.2 恢复验收与成本估算

### 验收判据

| 检查 | 通过条件 | 失败动作 |
| --- | --- | --- |
| SQLite 完整性 | `integrity_check` 返回 `ok` | 隔离备份并切换上一份 |
| 外键 | `foreign_key_check` 零行 | 阻止服务，查找截断或错误导入 |
| 发布链 | 父版本存在，`base_release_id` 和哈希字段完整 | 不允许恢复为当前 |
| 历史重放 | 固定 `release_id` 的结果行和摘要一致 | 标记 `unknown`，重新取证 |
| 缓存 | 只按发布重建，不能复用不匹配的图 | 丢弃内存缓存并重建 |

脚本的实测对象是 2 个发布、2 个空域限制、2 个暴露分区和一个历史查询。结果文件记录 Python、SQLite、平台、Git 提交和源码 SHA-256。YHT 的规模表明 2,400 栋建筑、每日 1 版、保留三年约 1,095 版；原始数据约 0.97 GB，加索引和历史约 2 GB，这是算术估算而非实测。

### 成本估算（模拟）

若将约 2 GB 热数据和一份同等大小的备份放在对象存储，按 2026-11-07 查阅的 AWS S3 Standard 官方价目 `$0.023/GB-month` 作为示例，存储费约 `4 GB × 0.023 = $0.092/月`，不含请求、跨区复制、出站和加密管理费用。保留 12 份月度备份约 24 GB，约 `$0.552/月`。这是公开单价乘以 YHT 的规模假设，不是 SkyRoute 生产报价；实际价格、区域和最低计费单位须在部署时重核。SQLite 本地文件不会因此产生云存储费用。

## 8.3 五项权衡、局限与结论

| 责任方向 | 选择 | 获益 | 代价与风险 |
| --- | --- | --- | --- |
| YHT | 灵活接入后以统一约束发布 | 接入多源，查询结构稳定 | 模式与质量门禁增加维护成本 |
| ZQO | 发布事务和不可变历史 | 读者看到完整快照，可追溯 | 发布期间不能直接修旧版本，存储增加 |
| LQ | 聚合暴露、最小权限和审计 | 降低敏感明细扩散 | 调试和复核需要受控流程 |
| ZC | 物化派生图按发布复用 | 重复查询低延迟 | 更新后必须识别受影响图并重建 |
| LJ | RPO/RTO 目标与备份成本平衡 | 可控制恢复损失和停机窗口 | 更高频备份、复制和演练增加费用 |

LJ 的取舍是：较短 RPO 需要更频繁 WAL/快照保护，较短 RTO 需要热副本、自动核验和预留容量；本地 SQLite 原型选择低运维和可复现，不足以证明多写高可用。改进方向是按目标规模演练增量备份、跨区副本、故障切换和恢复期间的 ZC 图重建，并把真实成本、RPO/RTO 和告警阈值写入部署验收。

综合结论是，恢复不是简单复制文件，而是“备份集合 + 完整性 + 版本链 + 历史重放 + 缓存重建”的验收闭环。任何一项失败都应停止受影响推荐并返回可解释的 `unknown` 或维护状态。
