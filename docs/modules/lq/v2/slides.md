# LQ v2 展示文字与讲稿

## 建议第5页：一条航线如何查到来源

**主标题**：航线结果的数据血缘

**主体图**：航线查询 → 发布R1 → 组件映射 → 物理暴露层R0 → 来源SRC-SYN；派生层D1同时关联模型1.0.0与编译窗口。绘制时保留逻辑发布和物理owner两个标签。

**证据表**：

| 航段 | 查询发布 | 暴露owner | 来源 | 模型 |
| --- | --- | --- | --- | --- |
| 1 | R1 | R0 | SRC-SYN | 1.0.0 |
| 2 | R1 | R0 | SRC-SYN | 1.0.0 |

**决策者要点**：更新后仍能解释旧结果；源或模型变化可定位需要重新验证的派生层。数据库是事实来源，JSON可以重建。

**讲稿（约60秒）**：这条查询使用的是R1发布，但没有变化的暴露数据复用了R0。我们通过数据库中的组件映射，找到具体区域、来源和模型版本，因此能回答“这段路线为什么得到这个风险解释”。本轮先用两段临时航线结果验证追溯SQL，正式查询结果表由下一棒接入。来源更新后，反向血缘能定位两个受影响派生层，系统再重算和复核。

**来源**：`op_c.sql`、`governance.json.operation_C`及invalidation；统一模式`release_component`、`risk_dataset`、`lineage_edge`；参考文献[1]。临时结果夹具与合成数据应在页脚标明。

## 建议第6页：谁能看、谁能改、谁能批准

**主标题**：访问控制与可追责的数据发布

**主体左侧**：调度员/运营人员看本机构200米摘要；安全管理员按策略看分区明细；系统管理员维护身份与策略。作者和审批人分离。

**主体右侧验证表**：

| 情境 | 实测结果 |
| --- | --- |
| 缺E/C、q不一致 | 拒绝入库/编译 |
| 时间缺口、伪写质检通过 | 拒绝封存 |
| 越权原表查询或写SQL | 拒绝 |
| 不同机构、停用账号 | 无可见行 |
| 作者审批自己发布 | 拒绝 |
| 原地修改已批准模型 | 拒绝，新ID修订 |

**共享与隐私权衡**：粗粒度展示减少细节，局部风险仍使用内部精确输入；200米和最少两个分区是演示参数，不代表匿名保证。

**讲稿（约60秒）**：风险数据既要能共享，也要限制用途。普通用户通过受限视图看本机构摘要，直接访问源表被拒绝。数据库同时核对E/C/q及时间覆盖，不能用一个“质检通过”标签掩盖缺口。发布审批绑定内容摘要，作者不能审批自己，也不能审批后换数据。模型旧版本保持不变，停用另记控制状态与审计。AI只辅助发现异常，最终变更仍需人工复核。

**来源**：`governance.json`、统一模式触发器、参考文献[1]–[4]。SQLite演示在服务持有连接的边界内运行，正式部署采用集中身份与数据库权限；保留策略90日热存/365日归档为内部设计，交LJ实施。
