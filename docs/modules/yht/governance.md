# 数据治理、质量与安全

## 1. 数据分类与生命周期

| 数据 | 分类 | 来源 | 生命周期 | 访问 |
| --- | --- | --- | --- | --- |
| 建筑轮廓、高度 | 城市基础空间数据（合成） | `SRC-FOOTPRINT`、`SRC-HEIGHT` | 随场景发布；新发布替代旧发布 | 查询只读；发布需质量门禁 |
| 地形格网 | 城市基础空间数据（合成） | `SRC-TERRAIN` | 随场景发布 | 查询只读 |
| 地面暴露分区 | 风险代理数据（合成） | `SRC-EXPOSURE` | 随场景发布；LQ 可替换 q | 查询只读；q 需标注来源与方法 |
| 空域限制 | 运行限制（模拟） | `SRC-AIRSPACE` | 带有效期；过期自动失效 | 查询只读；发布需版本与状态 |
| 查询结果 | 运行数据 | 由 Q1/Q2 生成 | 可按审计策略保留 | 仅调度/审计角色 |
| 发布清单 | 元数据 | `seal()` 生成 | 与发布同寿命 | 所有查询角色可读 |

生命周期按"采集 → 质检 → 发布 → 查询 → 归档"组织。采集阶段记录来源、获取时间、许可、精度；质检阶段跑结构、几何、属性、时间、覆盖规则；发布阶段生成五层版本与清单哈希；查询阶段绑定版本并返回覆盖瓦片；归档阶段保留只读快照和清单，不保留可变的中间状态。

## 2. 来源与血缘

每个空间对象都带 `source_id`，每个来源记录 `name/kind/license/acquired_at/valid/accuracy_xy_m/accuracy_z_m/method`。建筑还区分轮廓来源与高度来源（`footprint_source`/`height_source`），因为轮廓和高度往往来自不同采集方式，精度和更新时间不同。查询结果返回对象级来源和快照级五版，形成"对象 → 图层版本 → 发布清单"的链路。

血缘的边界要说清楚：我们能追到"这个对象来自哪个合成来源、属于哪一版"，不能追到"真实世界里哪次飞行、哪台传感器、哪一栋楼的哪一层"。合成数据的来源记录是结构示范，不构成真实数据出处。

## 3. 质量规则与发布门禁

质量规则分两级：

- **错误（阻断发布）**：重复 ID、环未闭合、自交、面积为零、越界、顶低于底、高度字段不一致、来源缺失、q 或 E/C 越界、q≠E×C、空域类型/字段非法、暴露分区未恰好覆盖一次、瓦片面积不等于场景面积、清单计数不一致、版本与内容不一致。
- **警告（不阻断，但查询必须 unknown）**：建筑高度缺失且 `quality=unknown`、瓦片 `complete=false`。这两类不是"数据错误"，而是"答案不确定"；发布可以保留，但任何依赖它的查询不能返回安全结论。

12 类故障注入全部检出，基线场景 0 错误 0 警告，34 个要素。规则实现见 `prototype/quality.py`，结果见 [results/quality.json](results/quality.json)。

## 4. 隐私、伦理与合规

- 场景全部为合成数据，建筑名称、来源名称、空域机构都是占位，不对应真实个人、真实地址或真实飞行活动。
- 地面暴露 `q=E×C` 是土地利用类别对应的代理值，`E`/`C` 也是合成假设，不是人口统计、不是个人轨迹、不是伤亡概率。把 q 用于风险评分时，必须同时报告"这是代理指标"，不能表述为"某区域人群风险为 0.78"。
- 不采集、不存储无人机操作员或居民的个人信息；若未来接入真实数据，应先做最小化、去标识化和访问控制，并明确保留期限。
- 空域限制是模拟参考，不能用于真实飞行决策；文档和 PPT 都标 `mock`/合成，避免被误读为有效 NOTAM。
- 数据许可写为 `CC0-1.0 (synthetic)`，只适用于本仓库合成数据；接入真实数据时逐源核对许可，不把仓库许可套到第三方数据上。

## 5. 安全与访问控制

原型没有实现认证和授权，但接口预留了治理所需的字段。生产设计建议：

- **角色**：调度员/运营只读查询；空域管理员可发布空域层；数据管理员可发布场景与来源层；审计角色可读发布清单和查询日志。发布权限按图层拆分，避免一个角色同时改建筑和空域。
- **完整性**：发布清单记录五版和内容哈希；查询预检拒绝版本不一致的请求。哈希不是签名，不能证明发布者身份；生产应加签名或发布审批记录。
- **可用性**：查询只读当前发布；发布切换用旁路构建 + 原子替换，避免半成品被读到。
- **审计**：Q1/Q2 返回 `versions`、`coverage`、`candidates`、`checked`、`reasons`；LJ 的验收可以据此记录"谁在什么版本上查了什么、结果是什么状态"。
- **拒绝服务**：Q1 半径和线段长度应设上限，避免一次查询扫全场景；原型未设上限，生产应在 API 层限制。

## 6. 保留、归档与更新

- 每个发布保留只读快照和清单；旧发布至少保留一个规划窗口 + 审计周期，具体时长由小组和课程要求确定，原型不写死。
- 动态更新采用新发布，不原地改；`results/update-example.json` 展示新增 NF-003 后 airspace 版本变化、旧版本查询返回 `version_mismatch:airspace`。
- 发布下线前检查是否仍有查询或审计引用；原型没有引用计数，生产应在发布表加状态字段（`active/retired`）。
- 归档格式用发布 JSON + 清单；SQLite 库可由 JSON 重建，因此库文件不是唯一副本。

## 7. 已知治理缺口

- 没有真实的数据主体、同意、跨境传输和敏感区域审查流程；这些在真实城市数据接入时必须补。
- 没有发布审批人和双人复核；`authority` 只是字符串，不能当授权凭证。
- 没有查询日志落盘和保留策略；当前只返回审计字段，不持久化。
- 没有密钥管理、传输加密和租户隔离；原型是本地单进程。
- 质量规则覆盖结构、几何、属性、时间、覆盖，未覆盖语义错误（例如"这栋楼实际不存在"）和来源可信度评级。
