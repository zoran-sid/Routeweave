# ZC v2 展示稿：建议2页（第7–8页）

交由 ZC 整合时按全组模板排版。结构为“结论标题 → 图表证据 → 条件 → 来源”，面向技术决策者；算法内容不超过半页。

## 第7页：规划慢在哪里——先分清数据库的账和算法的账

**主标题**：同一个 A*，只换取数方式：索引把取数从 34 ms 降到 0.17 ms

**副标题**：10,000 栋建筑的合成城市；查询结果完全相同，差别只在数据从哪里、取多少

**主图**：分组条形图，横轴为城市规模（200 / 2,400 / 10,000 栋），每组三根柱表示取数耗时（中位数，ms），另以折线标出 v1 A* 搜索耗时。

| 建筑数 | JSON 全量 | SQL 全量 | R*Tree | A* 搜索 |
| --- | --- | --- | --- | --- |
| 200 | 1.41 | 0.54 | 0.04 | 22.2 |
| 2,400 | 8.11 | 3.36 | 0.07 | 35.7 |
| 10,000 | 33.6 | 14.5 | 0.17 | 45.1 |

**右侧三条结论**：

- 整份发布读取随城市变大线性增长；R*Tree 只取搜索域附近约 72 个对象，10,000 栋时比 JSON 快约 200 倍。
- 三种取数方式交给规划器的输入逐字节相同（36/36），速度差异全部来自数据库访问路径。
- 剩余的 22–45 ms 是算法在航段上的相交检查；同一张图上 A* 比 Dijkstra 少扩展约 3.5 倍节点（125–214 对 465–747）。

**页脚**：文件 SQLite 3.54.1（WAL），Python 3.15.0，macOS arm64；每规模12个任务；合成数据。数据经 ZQO 发布事务与 LQ 风险数据集生成。来源：`docs/modules/zc/v2/experiments/results/access_paths.json`；课程《作业要求.pdf》第4–6页。

### 讲稿（约70秒）

这一页回答一个具体问题：规划服务慢，到底慢在数据库还是算法？我们把 A* 固定不动，同一批任务只换取数方式。整份读取发布的 JSON，或者用 SQL 读全城对象，耗时都随城市规模线性增长，一万栋时分别是 34 毫秒和 14 毫秒。用时空索引只取搜索域附近的对象，耗时稳定在 0.2 毫秒以内。

三种方式交给规划器的输入完全相同，所以这部分收益来自数据库设计。剩下的二三十毫秒是算法检查航段是否碰到建筑和禁飞区的时间；A* 的启发式在这部分把扩展节点减少到 Dijkstra 的约三分之一。两笔账分开以后，就知道各自该在哪里优化。

## 第8页：缓存派生图，并在新发布后只更新受影响的部分

**主标题**：缓存让查询降到 0.3 ms；新发布后按数据库变更记录更新，比全部重建快 7–16 倍

**左半：物化的收益与代价**

| 建筑数 | 按需搜索 | 构建派生图 | 命中缓存 |
| --- | --- | --- | --- |
| 200 | 22.2 ms | 48.7 ms | 0.58 ms |
| 10,000 | 45.1 ms | 128.8 ms | 0.31 ms |

- 同一（发布、搜索域、窗口、配置）第3次查询起收回构建成本。
- 缓存以发布为键，查询绑定的发布与图必须一致，数据库触发器拒绝错配。

**右半：新发布后的处理**（2,400 栋，24 张缓存图）

| 发布变化 | 沿用 / 修补 / 重建 | 全部重建 | 按变更处理 |
| --- | --- | --- | --- |
| 新增禁飞区 | 20 / 3 / 1 | 2.39 s | 0.35 s |
| 撤销禁飞区 | 22 / 2 / 0 | 2.39 s | 0.15 s |

- 变更来自 ZQO 发布事务写入的 `airspace_event` 与 LQ 数据集差异，检测耗时低于 0.2 ms。
- 48 张图与全部重建结果 0 处不一致；一条航线因新禁飞区变为不可行，失效判断直接决定结果正确性。
- 旧发布的缓存继续服务历史查询（24/24 命中）。

**底部选型条**：原型 SQLite + R*Tree（已实测）→ 部署 PostgreSQL + PostGIS（多用户写入、行级权限）；派生图留在规划服务内存，依赖关系记录在数据库。图数据库与 pgRouting 需要为每个发布×窗口物化约 1 万条边，暂不采用。

**页脚**：来源 `invalidation.json`、`access_paths.json`；技术比较见报告第6.5节；课程《作业要求.pdf》第2、4–5页。

### 讲稿（约75秒）

既然航段检查是主要成本，可以把整张可飞航段图预先算好。构建一次要五十到一百三十毫秒，之后每次查询只要零点三毫秒左右，同一个区域和时间窗被查询三次就划算。

难点在于数据会更新。我们的发布不可变，所以旧版本的缓存对旧版本永远正确，历史查询直接命中。新发布到来时，数据库已经记录了这次改动了哪些禁飞区、哪些风险值；只有与改动重叠的图需要修补，其余直接沿用。二十四张图中，新增禁飞区只需修补四张，用时从两秒四降到零点三五秒，而且每张图都与全部重建的结果逐一核对一致。其中一条航线确实因为新禁飞区变得不可飞，这说明失效处理关系到结果是否正确。

选型上，原型用 SQLite 加空间索引，部署时换成 PostgreSQL 和 PostGIS；派生图留在规划服务，由数据库记录它依赖哪个版本。
