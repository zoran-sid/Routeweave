# 第1至2页展示文字与讲稿

## 第1页 SkyRoute总体架构

我们研究模拟城市中的无人机配送。调度员需要一条满足建筑、禁飞、限高和风险约束的路线，管理员则持续更新限制。系统提供两项服务：查询三维航线，以及解释航段状态与来源。

架构把组员的成果连接起来：YHT组织三维数据，LQ提供风险输入与规则，ZQO将兼容的五类输入组织成完整发布，ZC进行航段检查与A*规划，LJ负责运行监控与恢复验收。当前已接入LQ和ZC原型，源数据库和运行服务按总体设计继续衔接。

对应材料：共同场景约定，LQ/ZC设计，ZQO架构与数据流图。

## 第2页 空域发布与查询一致性

这里重点说明更新期间如何保持查询一致。候选数据先校验并由独立评审员复核，发布目录在一个事务里写入完整发布、审计与待发送事件，再切换当前指针。查询固定一次发布后运行，结束时再检查当前版本，过时结果保留历史标签并重新规划。

我们用SQLite独立连接验证读写交错、失败回滚、并发发布和历史重放，新增20项测试，LQ与ZC原有40项回归也通过。同一合成场景中，禁飞使航程从116.57米变为129.28米，撤销后重新搜索恢复较短路线。LQ风险按时间窗计算，我们补上窗口标记，防止其他窗口误用。

对应材料：ZQO设计和evaluation.json；PostgreSQL事务与锁、AWS事务发件箱、SQLite事务官方资料。两页的完整来源也写在PPT备注中。

## 答辩准备

| 可能的问题 | 回答要点 |
| --- | --- |
| 固定旧版本会不会不够新？ | 固定版本保障一次计算完整，返回前用新读取核对发布，更新后重验；标明核对时间 |
| 既然有事务，为什么还要五类版本？ | 事务控制读取和提交，五类版本说明业务组合及来源，支持历史重放和模型兼容检查 |
| 发布失败后还能继续推荐旧路线吗？ | 目录不部分更新；是否可用还要看已确认的新限制，受影响业务必要时暂停并重新核验 |
| 为什么撤销也要重新规划？ | 原绕行路线虽然仍可用，解除限制后可能出现更短路线 |
| 验证是否代表生产系统？ | 已运行SQLite事务与LQ/ZC组合，PostgreSQL、外部身份、消息投递和跨机恢复需在部署环境验收 |

两页衔接：ZQO完成总体与发布介绍后，由YHT解释这些输入如何建模、存储和索引。
