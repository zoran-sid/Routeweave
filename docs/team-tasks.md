## 共同输入与工作边界

- 项目使用一个园区、基础路网和动态路况事件、同一已发布快照下的两项服务，以及 [AGENTS.md](../AGENTS.md) 中四条有向边的例题。
- 首轮对齐路段编号、方向、时间单位、事件有效期、版本标识和不可达返回。LJ 提出输入契约，LQ 整理字段定义，ZQO 明确发布语义，其余成员检查服务和权限所需字段。
- 五人均可从共同例题起草。依赖尚未定稿时写明假设并在接口确认后修订，避免将全部工作串成等待链。
- 规则表、伪代码、模型及手工推演作为基本交付。可运行原型按剩余时间选做，新增范围同步分配负责人和验证工作。
- 每个决定采用“问题—备选—证据或假设—选择—代价—适用条件”的简短记录。以下 D1–D5 可纳入各人三个成果中。

## 各成员的任务与完成标准

### 成员1 LJ 需求、数据接入与质量控制

**核心问题**：把原始路况事件变成可追溯、可发布的数据。

- [ ] **成果1：需求与访问负载表**。定义用户、两项服务、两类数据、规模与增长假设、读写频率、时效目标和数据生命周期；将关键需求关联到后续验证场景。
- [ ] **成果2：接入数据契约与处理规则**。定义输入字段、单位、时间语义、路段关联、必填约束和来源标识；给出校验、去重、乱序处理、过期处理与隔离流程的规则表或伪代码。
- [ ] **成果3：六条样例的质量检查记录**。覆盖正常、重复、乱序、过期、缺失路段和相互冲突的事件；逐条说明接受、隔离或拒绝的处理及理由，记录来源和处理状态。

**D1 设计决策**：比较按到达时间覆盖与按事件有效期及来源优先级处理的方案，说明新鲜度、正确性和处理成本的取舍；优先级属于需要说明依据的业务规则。

**验证与验收**：另一位成员依据同一规则表处理六条输入，应得到相同的质量判定与原因；有效期边界、重复和冲突的规则可明确复核。

**职责边界**：负责原始输入与质量规则；持久化模式、键和索引由 LQ 负责，版本发布协议由 ZQO 负责。

**交接**：向 ZQO、LQ 交付通过质量检查的输入契约，向 YHT 交付数据来源与质量追溯需求，向 ZC 交付异常输入样例。

**展示安排**：第1页讲“问题与访问负载”；第2页讲“接入流程、质量规则和一条异常样例”。个人记录：[LJ](handoffs/lj.md)。

### 成员2 ZQO 系统架构、版本发布与一致性

**核心问题**：保证事件更新、版本发布与一次查询使用一致的数据。

- [ ] **成果1：架构图与数据流图**。标明接入、存储、路况处理、查询服务和展示的职责及输入输出；说明选定部署形态与扩展瓶颈。
- [ ] **成果2：发布与查询时序及伪代码**。描述候选版本构建、验证、发布和查询固定版本的步骤；用一张时序图解释更新与查询交错时的行为，以及新增道路与只改变权重的差异。
- [ ] **成果3：故障恢复与资源取舍表**。用发布前失败、发布过程中失败和读取旧版本三个情境说明可观察结果、恢复动作及代价；说明历史版本保留、可用性与新鲜度的取舍。

**D2 设计决策**：比较直接修改正在读取的数据与构建后发布版本的方案，说明一致性、更新延迟、可用性和存储开销；最终协议需与 LQ 的版本模型一致。

**验证与验收**：手工走查查询与更新交错，以及一次发布失败；检查单次查询的路段和权重是否来自同一可用版本，失败后是否有定义明确的结果。

**职责边界**：负责端到端流程和版本发布协议；输入清洗由 LJ 负责，路由算法及算法比较由 ZC 负责。

**交接**：接收 LJ 的有效输入；与 LQ 对齐版本实体和保留策略；向 ZC 交付查询固定版本的接口条件，向 YHT 交付部署和发布权限需求。

**展示安排**：第3页讲“端到端架构与数据流”；第4页讲“版本发布、并发查询与故障时序”。个人记录：[ZQO](handoffs/zqo.md)。

### 成员3 LQ 数据建模、存储策略与查询设计

**核心问题**：让两类数据、版本与两项服务有一致的存储和访问定义。

- [ ] **成果1：数据模型与约束表**。定义路口、有向路段、路况事件、版本和查询记录的实体、字段、键、关系与时间约束；对接 LJ 的输入契约及 ZQO 的发布语义。
- [ ] **成果2：访问模式与存储策略表**。把查询条件映射到候选索引或图访问结构；说明当前状态与历史事件的组织方式、保留策略，以及是否需要分区、缓存或冷热分层并给出理由。
- [ ] **成果3：两个查询规范与推演**。定义起终点路线查询、路段状态与来源查询的输入、输出及异常结果；给出适合最终技术路线的查询或伪查询，沿样例追踪字段、版本及来源。

**D3 设计决策**：比较读取时根据事件计算状态与维护可查询的版本状态，解释读取成本、更新成本、历史追溯和存储开销；与最终技术选型共同定稿。

**验证与验收**：沿小路网检查实体关联和方向；演算一个事件生效或失效边界，并核对两项服务返回的版本、状态来源与不可达表达。

**职责边界**：负责持久化结构、访问策略和服务数据契约；路线查询中的 Dijkstra 细节由 ZC 负责，原始数据质量规则由 LJ 负责。

**交接**：与 LJ 对齐输入字段，与 ZQO 对齐版本与生命周期，与 YHT 对齐技术路线；向 ZC 提供有效图的数据访问方式及两项服务的输出契约。

**展示安排**：第5页讲“实体关系、字段与时间约束”；第6页讲“索引或图访问策略及两个查询”。个人记录：[LQ](handoffs/lq.md)。

### 成员4 YHT 技术选型、安全与治理机制

**核心问题**：以证据选定技术路线，并把安全治理落实到操作和数据。

- [ ] **成果1：技术路线决策表**。比较关系型时空存储配合路由组件与图数据库配合图算法；围绕实际访问、更新、版本、维护及成本条件论证选择，深入说明图数据技术的机制、适用范围和替代方案。
- [ ] **成果2：权限与威胁控制表**。区分查询、发布路况、维护路网和审计等操作的权限；说明身份认证、访问控制、传输或存储保护、审计以及位置日志最小化，关联具体威胁。
- [ ] **成果3：来源追溯与治理走查**。沿一条异常封路事件追踪来源、处理、发布和查询；说明所需元数据、血缘与审计字段、留存依据、潜在滥用或公平性风险及性能和维护代价。

**D4 设计决策**：以模型、更新和访问需求选择一种技术路线，并分析审计与历史记录保留对追溯能力、隐私和存储成本的影响；引用学术论文或官方技术文档。

**验证与验收**：走查一次无权限发布与一次合法发布，检查拒绝或接受的原因和审计证据；核对一次状态来源查询能否回溯到事件及发布记录。

**职责边界**：负责技术选择与安全治理；具体输入校验与质量样例由 LJ 负责，路由算法和性能实验设计由 ZC 负责。

**交接**：使用 LJ 的来源与质量信息、ZQO 的流程和 LQ 的查询条件；向三者反馈选型和治理字段，向 ZC 提供影响评估的资源与审计假设。

**展示安排**：第7页讲“技术路线比较与新兴技术机制”；第8页讲“权限、来源追溯与治理代价”。个人记录：[YHT](handoffs/yht.md)。

### 成员5 ZC 路径算法、正确性验证与性能评估

**核心问题**：定义可执行的路径查询逻辑，并说明如何验证正确性和性能。

- [ ] **成果1：路线算法规范与伪代码**。写明输入版本、路段方向、封闭过滤、权重前提、Dijkstra 步骤、终止条件、路径还原及不可达返回；说明复杂度、适用条件与快照数据访问的关系。
- [ ] **成果2：六种情境的正确性走查**。覆盖正常、封路绕行、不可达、更新期间查询、方向约束和同成本多解；给出输入、预期答案、判据及手算过程，至少完整追踪一次节点距离与路径选择。
- [ ] **成果3：受控性能评估与权衡表**。设计比较每次重算与同版本结果复用的方案，控制路网规模、更新比例、查询并发及缓存状态；列查询延迟、更新可见延迟、吞吐和资源成本的测量方法及适用范围。

**D5 设计决策**：比较每次重算与同版本结果复用，说明查询速度、更新成本和版本变化后的结果复用条件；CCH 作为拓展讨论，选择后才增加实现或实验工作。

**验证与验收**：对统一四条边手工核对 4 分钟、6 分钟及不可达结果；扩展方向与等成本样例；并发情境使用 ZQO 的时序及 LQ 的版本定义。未运行的性能实验保留为方案。

**职责边界**：负责路由机制与评估方法；每位成员完成自己模块的验证和结论，ZC 汇总跨模块指标；报告与 PPT 合并由待确定的组长协调。

**交接**：可先用统一小路网起草算法；随后接收 LJ 的异常样例、ZQO 的快照协议、LQ 的数据访问契约和 YHT 的资源假设，把矛盾或失败条件反馈给对应负责人。

**展示安排**：第9页讲“路径算法与正确性推演”；第10页讲“受控评估、关键权衡与设计结论”。个人记录：[ZC](handoffs/zc.md)。

## 均衡交付与合并

每人将三个核心成果压缩成可审阅的图、表、查询、伪代码或短说明；规模限制在当前园区场景。走查包含输入、步骤、预期结果、实际观察或手算结果及解释。未运行的性能实验标记为计划。

| 责任 | 五人共同标准 |
| --- | --- |
| 技术成果 | 三个核心成果，能追踪输入、处理规则与输出 |
| 判断与证据 | 一项关键决策，说明替代方案、依据和代价；引用与具体结论对应 |
| 验证 | 完成本模块走查；ZC 汇总跨模块指标，各人解释本模块的失败条件 |
| 报告与 PPT | 各自正文、两页 PPT、引用，以及供摘要和结论合并使用的2–3句素材 |
| 协作 | 完成一次交叉检查，更新个人记录中的实际成果、验证和下一步 |

组长协调格式、章节合并、摘要与总结合成以及排练；这些整合工作也记录为实际贡献。首版交付后根据实际投入和未完成依赖调整任务。最终贡献比例按实际产出与协作记录填写，合计 100%。
