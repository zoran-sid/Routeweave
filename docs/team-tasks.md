# SkyRoute v2 五人任务安排

更新日期：2026-11-06（Asia/Hong_Kong）。分支：`develop`。v1 交付保留在 `main`（标签 `v1.0-algorithm-baseline`）。每名成员交给 AI 的提示词见 [v2 提示词](v2-prompts.md)。

## 1 为什么重组

课程题目是《面向真实场景的新一代数据管理系统设计》（[课程要求](course-requirements.md) PDF第1页），要求围绕明确的数据管理问题论证架构、数据模型、技术选择、治理机制和设计权衡，原型属于可选佐证（PDF第1、6页）。

v1 已有实质的数据库工作：YHT 的关系表、三维 R*Tree、WAL 读写实验（[YHT 存储](modules/yht/storage.md)），ZQO 的 SQLite 事务、并发发布、失败回滚、幂等与不可变历史（[ZQO 验证](modules/zqo/evaluation.md)）。但研究主线、展示重点和整合深度偏向路径规划：

| v1 现状 | 问题 |
| --- | --- |
| 最突出的结果是 A* 扩展节点减少、路线绕开风险热点 | 回答的是规划方法是否有效，不是数据如何组织、查询、更新和保护 |
| YHT 与 ZQO 各有一套 SQLite 表，完整链路主要交换 JSON 快照 | 没有统一模式；哪些数据以数据库为准、哪些快照可重建、历史怎么查、重复存储代价多少，都没有展开 |
| 查询执行、事务边界、并发更新、历史组织的证据不如算法结果突出 | 数据库设计没有成为系统中心 |
| ZC 研究搜索、LQ 研究风险计算、LJ 验证返回结果 | 五人合起来自然形成一个规划原型 |
| 接入与集成、高可用与成本、隐私与伦理只零散提及 | 课程 PDF 第2、5页要求的覆盖面不完整 |

131项测试通过说明实现符合各自测试条件，不说明已体现数据管理设计的深度。

## 2 v2 定位

**SkyRoute：面向城市无人机配送的时空数据管理系统设计**
（SkyRoute: Spatio-temporal Data Management for Urban UAV Delivery）

**核心研究问题**：城市三维空间、动态空域和风险数据持续变化时，如何设计一个支持高效时空查询、一致性发布、历史追溯和安全访问的数据管理系统，为航线规划提供可靠输入？

- **航线规划是验证数据库设计的业务场景**。A* 继续使用，重点放在它如何取得正确、完整、版本一致的数据；算法原理在报告和 PPT 中各不超过一页。
- **新兴技术**：深入讨论**数据血缘与版本化派生数据管理**（课程 PDF 第4页“数据目录、元数据管理、数据血缘与数据可观测性”）：来源依赖、更新后的失效定位、派生数据重建成本、存储取舍。湖仓表格式的快照与时间旅行（Apache Iceberg 类）、PostgreSQL 时态表作为比较对象，说明为何本场景不选或何时会选。不罗列没有证据的热门技术（PDF第4页）。
- **主要证据是数据库实验**：索引前后访问成本、并发发布冲突、更新可见性、历史版本存储开销、恢复后数据完整性、规划查询的耗时分解。算法对照保留为应用效果验证。
- **范围**：合成数据、本地 SQLite 实测；PostgreSQL/PostGIS 等生产选型做设计论证，不推定未测量的性能。

## 4 统一数据库模式

**逻辑模型以 YHT 的 [数据字典](modules/yht/v2/data-dictionary.md) 为准**（16个实体：发布、发布层、来源、覆盖瓦片、空间对象、建筑、地形、空域限制与事件、暴露分区、风险模型、操作者、访问策略、血缘边、审计事件），它已把 v1 的 YHT 源数据表与 ZQO 发布目录合到同一套实体中。字段变更写入字典第9节变更记录。

可执行模式放在 `docs/v2/schema/`，由 YHT 按字典生成全部实体的 SQLite DDL 初版；其他成员在自己的棒次细化各自表组：

| 文件 | 内容 |
| --- | --- |
| `schema.sql` | 全部表、主键、外键、`CHECK`、索引、R*Tree 虚表与视图，SQLite 方言；按负责人分节 |
| `er.md` | ER 图（Mermaid）及每张表的用途、时间字段、版本关系 |
| `decisions.md` | 哪些数据以数据库为准、哪些快照可由数据库重建；哪些字段用 JSON 及理由；PostgreSQL/PostGIS 迁移时的对应写法 |
| `test_schema.py` | 在内存 SQLite 加载模式，开启 `PRAGMA foreign_keys`，验证约束、外键和代表性查询；CI 自动运行 |

表组负责人（各自细化本组表，需要改他人表组时记入 [问题清单](integration/issues.md)）：

| 表组 | 负责 | 示例 |
| --- | --- | --- |

| 发布与版本 | ZQO | 发布、发布层、空域事件；补 v1 的当前指针、失败尝试、待发送事件 |

| 操作 | 主责 | 配合 | 要回答的问题 |
| --- | --- | --- | --- |

| C 追溯某次航线所用的数据来源 | LQ | ZC | 从航线结果到发布版本、组件、源数据、风险模型版本的完整链路；谁有权查看 |

### 7.2 ZQO：事务、并发控制与版本管理（第2棒）

### 7.3 LQ：风险数据治理与数据库访问控制（第3棒）

1. 统一模式中加入风险派生、质量与访问表组：风险模型版本、派生风险层、质量检查结果、角色与权限、访问审计。
2. 质量约束落到数据库：`CHECK`、触发器或入库门禁，实测非法数据被拒绝（复用 v1 门禁）。
3. 权限矩阵（四类用户 × 表/视图 × 读写发布操作）；受限视图或行级过滤示例，实测越权查询被拒绝或被过滤；审计表内容与保留期。
4. 操作 C：从航线结果追溯到发布版本、组件、源数据和风险模型版本的 SQL 与执行计划（与 ZC 的查询追溯表衔接；ZC 尚未加表时先定义所需字段）。
5. 隐私与合规：暴露数据的聚合粒度与去标识化；伦理：风险规避造成的负担转移。AI 辅助治理（异常检测、敏感字段分类）简述适用条件与人工复核。
6. 权衡：数据共享价值 vs 隐私保护（暴露数据的空间粒度）。
7. PPT 建议主题（页数可按内容增减）：第5页：血缘与来源追溯；第6页：访问控制、审计与隐私。

### 7.4 ZC：面向规划的查询负载与性能（第4棒）

**已完成**（分支 `zc/v2-query-workload`，2026-11-07）：结果表组与正式操作 C、取数路径与缓存失效实验、第6章、第8.1节、附录 A、第7–8页。审阅 LQ：12项探针11项通过，新问题 LQ-V2-02 见[问题清单](integration/issues.md)。入口见 [ZC v2](modules/zc/v2/README.md)。合入 `develop` 后**第5棒 LJ 可以开始**。

1. 统一模式中加入查询与结果追溯表组：查询运行、航线结果、航段来源映射、派生图缓存（以发布版本为键）。
2. 定义规划查询负载：Q1 需要读取哪些表、按什么条件过滤、每次任务的数据量。
3. 主实验：固定 A* 和同一批任务，比较数据访问方式——(a) v1 JSON 快照全量装载，(b) SQLite 全表扫描，(c) R*Tree 按航线走廊预过滤，(d) 按发布版本缓存的派生图。分别测量数据库查询、数据装载、构图、搜索耗时，并随建筑数扩展；分清收益来自数据库设计还是算法。
4. 缓存失效：发布或撤销后，整图重建与按受影响范围失效的成本与正确性对比。
5. 第6章技术比较（简表）：SQLite+R*Tree、PostgreSQL+PostGIS、图数据库、PostGIS+pgRouting；给出选型与理由。
6. A*/Dijkstra 对照压缩为一段及附录。
7. 权衡：预计算/物化派生图 vs 数据新鲜度。
8. PPT 建议主题（页数可按内容增减）：第7页：规划查询的耗时分解；第8页：缓存失效、派生图重建与选型（算法不超过半页）。

### 7.5 LJ：运行保障与恢复验收（第5棒）

1. 备份与恢复流程：SQLite 在线备份或 WAL 检查点；RPO/RTO 设计依据。
2. 恢复后一致性核验实验：`PRAGMA integrity_check`、`PRAGMA foreign_key_check`、发布链完整性、用恢复后的数据重放一次历史查询并与保存结果比对；人为制造损坏或中断，验证能被发现。
3. 保留策略：历史版本、审计、待发送事件与查询结果的保留期和归档方式。
4. 监测指标：数据新鲜度、发布失败、WAL 大小、查询错误率，与 ZC 的指标对齐。
5. 第3.3节部署设计与第8.2节成本估算（按 YHT 规模）。
6. 第8.3节：汇总五人权衡，写风险、局限与改进方向。
7. 权衡：恢复目标（RPO/RTO）vs 成本。
8. PPT 建议主题（页数可按内容增减）：第9页：备份恢复与一致性核验；第10页：权衡、局限与结论。

## 8 串行执行与交接

```text
YHT → ZQO → LQ → ZC → LJ → ZC（整合）→ main
```

提交前全程异步。按依赖串行，每人只读已合入 `develop` 的真实成果，每个 AI 完整执行一次即可，避免猜测和返工。

**开工条件**：上一棒的 PR 已合入 `develop`，`checks` 通过，交接记录已更新。YHT 第一棒已在进行，合入前按第7.1节补齐。若 `docs/v2/schema/` 缺失，ZQO 按 [v2 提示词](v2-prompts.md) 的兜底步骤处理。

**审阅方式**：

1. 作者 PR 的 `checks` 通过后自行合入 `develop`（不要求审批）。
2. 下一棒的 AI 第一步审阅上一棒的成果：模式能否加载、实验能否复现、结论与证据是否一致。问题记入 [问题清单](integration/issues.md)，由原作者修复，不代改他人结论。
3. ZC 整合时全量复核。

**完成后**：在群里通知下一棒“已合入”。
